# 挥拍检测实现与验证

日期：2026-10-05。分支 `dev-1`。固件已使用 bundled Arduino CLI 编译并上传至确认过的 COM3 Uno。当前负向版本占用 16,858 字节 Flash（52%）及 776 字节全局 RAM（37%）；此前 Stage B 正向版本为 16,834 字节。当前编译通过。

## 检测流程

静止校准后，先读取 `DETECT,ON` 命令再开启检测。原始数据流与检测分别控制；正式运行可关闭原始 IMU 输出，仅接收 BEAT。校准、传感器读取失败和 `DETECT,OFF` 会清除检测状态。

当前右手佩戴方式以去零偏后的 gx 负方向为下挥，`directedGyro = -(gx - bias)`。此前正向参数的记录作为历史结果保留，最新分离验证见下文。使用三个状态：

1. WaitRelease：等待 directedGyro 低于释放阈值，避免启用检测时截取半个动作。
2. Ready：directedGyro 和运动分数超过高阈值后开始动作。
3. Tracking：记录最大 directedGyro 的时间戳和整个动作的最大运动分数；directedGyro 低于释放阈值后验证动作时长与拍间隔，最多输出一次 BEAT。

超时或拒绝的动作回到 WaitRelease。采样间隔超过 30 ms、非有限数值或时间戳重置会取消未完成动作。时间差使用 32 位无符号运算，允许毫秒计数器正常回绕。

## 当前参数

参数集中在 `arduino/AirConductor/config.h`，依据本次右手数据选取，后续多人测量可调整。

| 参数 | 值 |
| --- | ---: |
| 主轴及方向 | gx，负向（原先正向） |
| directedGyro 启动 / 释放阈值 | 0.8 / 0.25 rad/s |
| 运动分数启动阈值 | 1.5 |
| 接受动作的最低峰值分数 | 4.0 |
| gyro 权重 | 2 |
| 有效动作时长 | 90–600 ms |
| 最小峰值间隔 | 280 ms |
| 允许最大采样间隔 | 30 ms |
| intensity 满量程运动分数 | 16 |

运动分数为 `abs(|accel|-|calibrated_accel|) + 2*|gyro-bias|`。`BEAT,<timestamp_ms>,<intensity>` 的时间戳取最大 directedGyro 处，即当前安装的最负 gx；intensity 取最大运动分数除以 16 并限制到 0–1。它表示相对动作强度，不是绝对物理力度或音乐音量。

等待释放可以确认动作并减少重复计数，但事件到达晚于峰值。后续浏览器估计拍间隔应使用 BEAT 内的设备时间戳；播放响应仍受到确认延迟影响，需要在音乐接入后评估。

## 自动检查与回放

17 项测试通过，其中 8 项通过本机已有 g++ 编译并运行固件同一份 `stroke_detector.cpp`。覆盖静止和负向 directedGyro 回程、单次动作及峰值时间/强度限制、短促抖动/长动作、低强度正向回弹、短时强回弹不会阻止下一次下挥、重复触发、采样中断/设备重启/非有限输入、计时回绕和手动 reset，以及短方向提示计划。

初始佩戴数据 `imu-20261005-151642-673039.csv` 使用第一版检测器回放产生 62 个候选事件，初始静止段为 0；释放确认延迟中位数为 130 ms，最大 340 ms。准备与停止提示段实际存在动作，分段边界也受反应时间影响，不能根据这些候选数推导识别准确率。

原生回放使用打印出来的原始数据和校准值计算特征，数值精度与 Uno 内部浮点计算存在小差异；独立实机验证仍是主要依据。

## 独立完整实机测试

记录 `imu-20261005-153656-006808.csv` 使用初始 Stage B 固件，并未添加最低峰值分数过滤。包含 12,606 个有效 IMU 样本和 69 个 BEAT，100.000 Hz，最大采样间隔 12 ms；无无效帧、时间戳重置、重复时间戳或超过 30 ms 的采样间隔。81 个主机提示正常执行，检测启停均收到确认。

| 提示段 | 输出拍数 | 拍间隔中位数对应 BPM |
| --- | ---: | ---: |
| 初始静止 | 0 | — |
| 10 次分离下挥 | 10 | — |
| 10 次分离回程 | 0 | — |
| 60 BPM，12 声提示 | 13 | 61.86 |
| 90 BPM，18 声提示 | 18 | 92.31 |
| 120 BPM，24 声提示 | 22 | 115.38 |

所有 BEAT 峰值时间戳都能匹配原始 IMU 样本，intensity 合法；峰值样本接收至 BEAT 接收的延迟中位数 125 ms，最大 281 ms。准备/停止提示段共出现 6 个事件，这些段的波形包含实际动作和跨段的末拍。120 BPM 段也有动作延续到停止提示段；没有逐拍独立标注，不能直接将提示数与段内事件差值全部认定为漏拍。

60 BPM 段出现一个额外低强度正向候选，其 intensity 为 0.157，即峰值运动分数约 2.51。添加最低峰值分数 4.0 后，同一记录回放从 69 个事件降至 67 个：60 BPM 段变为 12 个，另去除准备段一个低强度事件；10 个分离下挥、18 个 90 BPM 段事件和 22 个 120 BPM 段事件保持不变。最终固件包含这一过滤条件；它可能拒绝很轻的挥拍，当前目标是明显下挥。

首轮曲线：`recordings/imu-20261005-153656-006808.beats.png`。首轮摘要/拍点分析/原生回放均保留；修正回放另存为 `recordings/stage-b-energy-filter-replay.csv` 和 `.json`，没有覆盖旧结果。

## 修正后的短测与时长过滤

记录 `imu-20261005-154450-971104.csv` 验证峰值分数过滤版本，共 3,839 个有效 IMU 样本，100.000 Hz，最大采样间隔 13 ms，无无效帧或时间戳异常。静止与准备段为 0 拍，60 BPM 提示段为 13 拍，停止提示段为 1 拍。用户不确定实际下挥总数，因此没有据此计算准确率。

波形中额外的一个正向候选峰值分数约 6.38，但只持续 50 ms；附近另一回弹持续 60 ms。已记录正常下挥的持续时间不低于约 140 ms（首轮 60/90/120 BPM 段分别至少 200/160/160 ms）。因此最终最短动作时长从 40 ms 调至 90 ms，同时保留最低峰值分数 4.0。

新时长条件在短测记录中去掉该 50 ms 事件：60 BPM 段回放为 12 拍，停止段仍保留一个真实动作候选；完整首轮回放仍保留全部 10 个分离下挥和 18 个 90 BPM 段事件。两轮回放结果分别保存在 `stage-b-duration-filter-short-replay.*` 和 `stage-b-duration-filter-full-replay.*`，原始结果不变。

最终参数针对当前明显下挥；很轻或短于 90 ms 的动作可能被忽略。一般手臂调整若满足相同方向、强度和时长条件，仍可能形成事件，这需要后续更丰富的动作数据验证。

## 最终固件独立复测

记录 `imu-20261005-155210-468771.csv` 使用最终固件（峰值分数 ≥4.0、时长 90–600 ms），重新静止校准后进行另一轮 12 声 60 BPM 提示测试：

- 3,837 个有效 IMU 样本，100.000 Hz，最大间隔 13 ms；无无效帧、重复时间戳、设备重置或超过 30 ms 的采样间隔。
- 60 BPM 提示段输出 12 个 BEAT；初始静止、准备及停止段均为 0。
- BEAT 数据合法，12 个峰值时间戳全部匹配原始样本；同代码回放也得到相同的 12 个峰值时间戳。
- 拍间隔中位数 930 ms，对应 64.52 BPM。这是本轮实际动作峰值节奏，不是已经实现的浏览器 BPM 估计，也不等于提示音的精确 60 BPM。
- 峰值样本至 BEAT 接收的延迟中位数 125 ms，最大约 266 ms；检测器原生回放的释放确认延迟中位数 124.5 ms，最大 260 ms。接收延迟包含主机处理与串口排队，不能直接当作声音响应延迟。
- 提示计划正常完成，检测与数据流启停均收到确认，无截断尾帧。

最终曲线和报告：`imu-20261005-155210-468771.beats.png`、`.beats.json`、`.summary.json`；原生回放为 `.replay.csv` 和 `.replay.json`。原始数据均留在 `recordings/`，未提交。

额外串口控制检查确认：未校准时 DETECT,ON 返回 NOT_CALIBRATED；DETECT,OFF 在未校准状态也能使用且不关闭独立的原始数据流；活动数据流期间 SCAN 被拒绝，关闭数据流后能读取地址和身份；停止后无输出。记录为 `recordings/stage-b-control-checks.json`。本次关闭串口后检测处于关闭状态，后续重新连接仍需校准再启用。

当前结果支持推进浏览器串口接入和节奏估计。多人、不同佩戴方向、轻动作、150 BPM 和长时间自由挥拍的独立验证尚未完成；这轮提示数据不能替代逐拍真值标注。

## 使用

### 当前佩戴方向修正与独立核对

浏览器短测后，用户确认单独下挥不计拍、单独上抬稳定计拍。将 `STROKE_DIRECTION` 从 `+1` 改为 `-1`，其余阈值保持，重新编译并上传 COM3；无需猜测物理 XYZ 朝向。

独立记录 `imu-20261005-164137-282110.csv` 采用 3 组下挥/停住、上抬/停住，动作间隔 2 秒：

- 去偏 gx 下挥峰值为 -2.009 / -2.104 / -2.031 rad/s；上抬峰值为 +1.705 / +1.767 / +1.746 rad/s，三组均反号。
- 实机 BEAT 全部匹配下挥原始样本：下挥 3 拍，上抬 0 拍，校准/静止/准备/结束均 0 拍。
- 3,640 个 IMU 样本，100 Hz，最大间隔 12 ms，无非法帧、重启、重复或超过 30 ms 的采样间隔；启停均收到回执，关闭串口正常。
- 当前配置的同代码回放得到相同 3 个下挥峰值，释放确认延迟中位数 170 ms、最大 180 ms；峰值样本接收到 BEAT 接收延迟中位数 172 ms、最大 187 ms。
- 用旧 `--direction 1` 回放同一数据，只输出 3 个上抬事件，说明这次问题来自方向符号；对应结果为 `stage-c-original-sign.csv/.json`。

回放默认读取固件轴和符号，历史正向记录可使用 `--axis gx --direction 1`。所有结果是本次固定佩戴方式的分离动作核对，不能作为通用方向识别或总体准确率。静止校准修正零偏，不会自动选择下挥方向。

```powershell
python diagnostics/read_serial.py --port COM3 --validate-beats
python diagnostics/analyze_beats.py recordings/<验证文件>.csv --plot
```

`--validate-beats` 等待启动与静止校准，收到 READY 后发送 DETECT,ON，再通过语音和音调引导 10 组分离下挥/回程与 60/90/120 BPM 连续挥拍。结束先关闭检测，再停止原始数据流。所有原始数据、摘要与曲线留在 `recordings/`，不进入 Git。

`--check-60` 用于修正后的短测：静止、12 声 60 BPM 提示、停止段。提示计划在校准后持续 36 秒；包含启动等待的默认时限为 65 秒。可用 `--boot-wait 15` 留出更长的准备时间，语音会读出所配置的等待秒数。

拍数分析按 BEAT 峰值对应的原始 IMU 样本分段，而不是按稍后收到 BEAT 的时间分段；同时报告未匹配峰值、非法 BEAT 和接收延迟。主机提示标记仍不是逐拍观察真值。
