# 浏览器串口与节奏测量（Stage C）

## 当前结果

已实现网页串口连接、启动握手、静止校准、检测开关、BPM、拍点脉冲、相对强度与 CSV 导出。Stage C 完成时，25 项 Node 测试和 Vite 生产构建通过。2026-10-05 用户已确认真实 Chrome 页面显示“已连接”及“校准完成”，完成三段提示动作并导出 CSV。本页记录串口与节奏测量的阶段结果；后续已实现音乐播放，见 [Stage D](music-playback.md)。摄像头尚未接入。

沿用 Stage B 的检测器与协议；本阶段发现当前佩戴方向符号反了，已修正符号并重新上传 Uno。最终运行链路为 Uno → USB → 网页，不需要 Python 桥接或 Lab4 文件。

## 操作

1. 在 `web` 目录运行 `npm run dev`，用 Chrome 打开显示的本机地址。Web Serial 需要安全上下文；本机 localhost 可用于开发。[Chrome 官方说明](https://developer.chrome.com/docs/capabilities/serial)
2. 关闭占用串口的 Python 采集器和 Arduino Serial Monitor。点击“连接设备”，在浏览器设备选择器中选 Uno 当前串口（目前 COM3）。等待启动完成，显示“已连接”。打开串口可能重启 Uno。
3. 右手保持本次验证过的安装方向，支撑手臂。点击“静止校准”，5 秒准备后采集约 2.5 秒；保持静止直到“校准完成”。检测到移动时会提示重试。
4. 点击“开始检测”。连续明显下挥，每次抬手回位；通常第 3 个有效拍点产生首个 BPM，第 4 个进入“跟随挥拍”。收到的 BEAT 数和用于计算节奏的间隔是不同统计。
5. 停挥超过 2.5 秒显示“停挥”，保留上次 BPM；恢复时建立新的间隔历史。点击“停止检测”会清空当前测量。重新校准、设备重启或重连也会清空测量。
6. “导出拍点记录”保存本页收到的协议事件（最多最近 10,000 条）与 BEAT：包含接收 UTC、网页经过时间、设备峰值时间和相对强度。导出覆盖本页多次连接，不含六轴原始数据；本地时间用于接收记录，不用来计算 BPM。
7. 调试区可独立打开六轴数据流。点击“断开设备”先发送停止检测/数据流，再取消读取并释放串口；下次连接后重新校准。

## 节奏估计

`tempo.js` 使用 Uno 的无符号毫秒峰值时间戳计算间隔，处理正常时钟回绕及设备重启。串口消息在回程释放后才发出，因此不能用网页接收间隔替代峰值间隔。

支持 50–180 BPM。小于约 333 ms 的间隔被过滤，并保留上一个有效时间锚点；大于 1,200 ms 的间隔不用于估计。最近最多 5 个间隔取中位数，再以 0.35 权重平滑。已有基准后，变化超过 25% 时，最近 5 个合法间隔中至少 3 个同向偏离才确认速度变化，以减少单次漏拍影响，同时允许动作自然波动。由此，确认和读数收敛需要数拍；这不是逐拍瞬时速度。

网页收到的拍点仍显示脉冲和计数，间隔过滤只影响 BPM。相对强度来源于固件运动分数，不是声压或已校准音量。没有 BPM 时显示“—”，不把默认音乐速度当成测量值。

## 本轮真实浏览器验证

输入：`Final/tmp/air-conductor-beats-2026-10-05-16-31-51.csv`；提示时间：`recordings/browser-cues-20261005-163025-078754.json`；分析与当前算法回放：`recordings/browser-validation-20261005.json`。这是方向修正前的采集，用户随后确认其当前安装的上抬才被计拍。浏览器控制工具连接失败，因此页面操作由用户完成，CSV 是实际串口回执与拍点证据。

CSV 包含一次 BOOT、启动停止命令和 STATUS、一次移动校准拒绝、两次成功校准、DETECT,ON，以及 39 个 BEAT。36 声提示均按计划执行，无跳过，调度最大迟到约 9.7 ms。按每段首声至停止提示后 1 秒的接收窗口分组，给释放确认留出时间：

| 提示 BPM / 12 声 | 接收拍数 | 全段峰值间隔中位数 | 当前算法回放末值 |
| --- | ---: | ---: | ---: |
| 60 | 11 | 1,055 ms（56.87 BPM） | 59.67 BPM |
| 90 | 12 | 650 ms（92.31 BPM） | 91.20 BPM |
| 120 | 13 | 450 ms（133.33 BPM） | 121.36 BPM |

三个段外事件分别发生在开始提示前或速度准备期间。120 段初始动作较快，末 5 个峰值间隔中位数为 500 ms；12 个事件的相对强度达到上限，不表示传感器原始量程已饱和。初版变速确认遇到间隔波动会反复丢弃候选，末值停在 138.49 BPM。改为窗口内三个同向偏离确认后，同记录末值为 121.36 BPM，并新增真实序列回归测试；该修正是在采集后回放验证，尚未再次进行佩戴采集。

提示数不代表已确认动作次数，段内多/少事件不能直接归为重复检测或漏拍。CSV 不包含六轴数据，不能从本文件确认下挥与回程的物理方向，也不能由设备绝对时钟与网页时钟直接相减推算确认延迟。

导出时检测仍开启；用户随后点击停止并确认页面显示“未开始”。导出文件中没有最后的 DETECT,OFF 回执。用户断开网页后，CLI 成功上传且 Python 成功独占 COM3 完成方向采集，串口可供后续程序使用。真实拔插重连及停挥状态的页面观察仍待后续检查。

## 反馈时机与下一步

固件在 directedGyro 峰值记录拍点时间，在该值低于释放阈值后发送 BEAT。网页闪动发生在收到消息时，可能已经开始抬手回位。用户进一步确认“单独下挥不计拍，只有上抬计拍”，因此本轮问题是方向符号，不仅是反馈延迟。

已将当前安装的方向改为 `-(gx - bias)` 并上传。3 组独立分离动作原始数据确认下挥 gx 为负、上抬为正；实机与当前配置回放都是下挥 3 拍、上抬 0 拍、静止 0 拍。旧正向配置回放同一数据得到上抬 3 拍。当前释放确认中位数约 170 ms，细节见 [方向修正验证](stroke-detection.md)。这一延迟在方向修正后仍存在。

自动测试使用模拟串口和真实 Stage B 拍点夹具，不能替代真实浏览器连接验证。Stage B 的 12 拍记录来自 60 BPM 提示，但实际峰值间隔中位数为 930 ms；网页应跟随实际动作，而不是强制输出提示速度。

方向问题已用分离动作确认并修正。本地 MIDI 播放、手动变速、暂停/恢复及挥拍 BPM 接管已实现；本轮真实佩戴记录和用户试听确认音乐有变化、暂停后可继续，结果与慢段限制见 [Stage D](music-playback.md)。网页重连后仍需重新校准。需要佩戴动作时提前通知。

短测可在网页已校准、已开始检测后运行 `python diagnostics/browser_guide.py`，提供 60/90/120 BPM 各 12 声的本地语音/提示音，段间静止 6 秒。此脚本只播放声音，不打开串口，因此可与网页并行。提示时间保存到 `recordings/browser-cues-*.json`；完成后点击网页“停止检测”和“导出拍点记录”，结合 CSV 与提示时间评估，不把提示次数当成已确认的动作次数。
